# BURNING FRONT — 개발 우선순위와 개발 계획

버전 1.0 · 2026-11-25 · 기획서 `docs/game-plan.ko.md`(v1.2)를 만들기 위한 순서입니다. 일정(날짜·기간)은 두지 않습니다.
구조는 `docs/ARCHITECTURE.md`, 유닛 데이터는 `docs/data-form-roadmap.md`, 규칙은 `SPEC.md`를 따릅니다.

## 1. 우선순위 원칙

1. **놀 수 있는 것부터.** 새 구조로 1 대 1 한 판이 휴대폰에서 돌아가는 것이 첫 목표입니다. 그 전까지 legacy v214는 그대로 플레이 가능하게 둡니다.
2. **위험한 것을 먼저 확인.** 휴대폰 성능(PixiJS), 미션 시스템, AI는 콘텐츠를 만들기 전에 작게 검증합니다. 늦게 터지면 만든 콘텐츠를 버려야 합니다.
3. **도구 다음에 콘텐츠.** 데이터 형식, 미션 데이터, 지도 도구가 먼저이고, 36개 미션은 그 다음입니다. 1인 개발에서 콘텐츠를 손으로 하나씩 만들면 끝나지 않습니다.
4. **한 번에 하나.** 진행 중인 단계는 하나만 둡니다. 새 아이디어는 "나중에" 목록(§3의 Could / Won't)으로 보냅니다.
5. **단계마다 플레이 가능한 빌드.** 단계가 끝날 때마다 휴대폰에서 실행해 봅니다. 동기 유지와 방향 확인을 위해서입니다.
6. **규칙은 테스트로 지킨다.** 로직은 모두 Node 테스트가 있고, `npm run check`와 `npm test`가 통과해야 커밋합니다.

## 2. 우선순위 등급

| 등급 | 뜻 |
| --- | --- |
| **P1 필수** | 없으면 게임이 성립하지 않음. 공개 1차 전에 반드시 |
| **P2 중요** | 게임의 맛을 크게 좌우. 공개 1차 전에 하되, 막히면 공개 2차로 미룸 |
| **P3 있으면 좋음** | 시간이 남으면. 공개 후 업데이트로 가능 |
| **제외** | 이번 범위에서 하지 않음 |

## 4. 개발 단계 (순서대로)

각 단계는 **완료 기준(관문)**을 통과해야 끝나고, 그 다음 단계가 시작됩니다.

| 단계 | 내용 | 완료 기준 |
| --- | --- | --- |
| **D0 기반 정리** | SPEC 정리(결정 반영), 작업 방식 확정(§7), legacy 수치 스냅샷 도구(`tools/oracle`: v214를 헤드리스로 실행해 유닛·지형·건물 수치 저장) | `data/legacy-snapshot/` 생성, 문서 갱신 |
| **D1 데이터 기반** | CoH3 받기·조사(완료) → **구조·유닛 상태 설계(`docs/unit-state.md`, 완료)** → 어휘·검사 도구(D1-3, 완료) → 스키마·범주 프로필(D1-4, 완료) → 가져오기 도구 시범(미군·독일군 6개 유닛) | 시범 유닛이 스키마 통과, CoH3 변환 보고서(v214 차이는 참고) |
| **D2 규칙 엔진** | `logic/` 아래에서 위로: hex → movement → vision → combat → crew·status → turn(반격·경계 사격) → capture·economy → victory(승점). store·commands·events | 화면 없이 Node에서 명령만으로 1 대 1 한 판 끝까지 진행하는 테스트. 축별 상태 기계 전이표 테스트 통과. 수치는 CoH3 기준(v214는 동작 참고) |
| **G 그레이박스 플레이 (데이터 검증)** | 4진영 전체 데이터 가져오기(D1-5 가져오기 도구 확장) → 아트 없는 회색 화면(헥스·색 토큰·글자 라벨, Canvas 2D)으로 규칙 엔진 위에서 1 대 1 플레이 → 디버그 표시(명중·관통 확률, 발수, 피해, 사거리, 상태 축·상태 플래그) → 자동 검증 보고서(유닛별 생성·사격·사망까지 걸리는 턴(TTK) 표, 비용 대비 효율, 사거리·탄약·재장전·곡사 주기 점검) → 이상 수치 수정 | 모든 유닛이 생성·이동·사격·사망 가능, TTK 표가 기준 범위 안(벗어나면 사유 기록), 개발자가 그레이박스로 진영 조합별 1 대 1을 여러 판 플레이하고 데이터 검토 완료 서명 |

## 5. 단계별 세부 작업 (첫 세 단계)

Claude 세션 하나에 작업 하나가 원칙입니다. 작업마다 "시스템 폴더 · 테스트 · 완료 조건"이 있습니다.

**D0 기반 정리**

1. SPEC.md 정리: 섹션 10의 결정을 본문 규칙으로 옮길 준비, 새 규칙(경계 사격 확대, 제압 2단계, 변 엄폐, 치명타)을 섹션 10에 추가.
2. `tools/oracle/snapshot.js`: legacy 빌드를 Playwright로 열어 `UNIT_ROSTER`, 키트, 베테랑, 지형, 건물, 교리, 가격, 지도를 JSON으로 저장.
3. 작업 카드 양식(§7)과 `docs/dev-log.md` 시작.

**D1 데이터 기반** (`docs/data-form-roadmap.md` 1~5단계)

1. `tools/coh3/fetch.js`: coh3-data 커밋 고정, `german`, `american`, `afrika_korps`, `british`, `common`의 weapon·ebps·sbps 받기, 쓰는 레코드만 추출.
2. `tools/coh3/census.js`: 4진영 범주별 블록 사용표.
3. `data/rules/vocab.json`, 공통 타입, `tools/validate.js`(+테스트).
4. `data/schema/*.schema.json`, `profiles.json`, 범주별 손 샘플.
5. `tools/import-coh3` 시범: 소총병, 셔먼, 57 mm 대전차포, 81 mm 박격포, M1919 기관총 팀, 포좌 1종.

**D2 규칙 엔진** (각 시스템 = 작업 1~3개)

1. `logic/hex`, `services/rng`
2. `logic/fsm`(상태 기계 도우미), `logic/state`(유닛 상태 `unit.js`), `logic/events`, `logic/commands`, `logic/store`
3. `logic/movement`(이동 비용, 경로, 선회, 후진)
4. `logic/vision`(시야, 시야선, 은폐)
5. `logic/combat` 공식 → 해결 → 미리보기 (수치는 CoH3, v214와의 차이는 참고 보고)
6. `logic/crew`, `logic/status`(제압·고착·후퇴·베테랑·탄약)
7. `logic/turn`(턴 순서, 행동 상태 기계, 반격, 기관총 경계 사격), `logic/lifecycle`(사수 전멸·버려짐·재운용·잔해)
8. `logic/capture`, `logic/economy`, `logic/build`
9. `logic/victory`(승점), 명령만으로 한 판 끝내는 통합 테스트

**G 그레이박스 플레이 (데이터 검증)** — 규칙 엔진(D2) 다음, 첫 화면(D3) 전. 그림 대신 데이터를 보는 단계입니다.

1. 가져오기 도구를 4진영 전체로 확장(`data/units/<진영>/`), `npm run check`로 스키마·프로필 통과.
2. `src/presentation/greybox/`: Canvas 2D 회색 화면. 헥스는 지형별 회색 단계, 유닛은 진영 색 원 + 종류 글자 + 체력 숫자, 이펙트 없음.
   입력은 정식 컨트롤러(`presentation/controller`)를 그대로 써서 D3에서 버리지 않습니다.
3. 디버그 표시: 선택 유닛의 사거리·최소 사거리, 대상별 명중·관통 확률과 예상 피해, 발수, 상태 축 6개와 상태 플래그, 곡사 흩어짐 범위.
4. `tools/greybox/report.js`: 화면 없이 규칙 엔진으로 유닛 쌍 대결을 수천 번 돌려 TTK 표(몇 턴 만에 쓰러뜨리는가), 비용 대비 효율, 탄약 소진 턴, 곡사 주기별 피해를 보고서로 만듭니다.
5. 기준(TTK 범위, 비용 효율 범위)은 `data/balance/greybox.json`에 두고, 벗어난 유닛은 수정하거나 사유를 기록합니다.
6. 그레이박스 빌드를 휴대폰에서도 열어 보고(조작감 확인), 데이터 검토 완료를 dev-log에 서명합니다.

D3 이후 단계의 세부 작업은 각 단계 시작 때 같은 방식으로 나눕니다.

**규칙:** 에셋을 추가할 때마다 `assets/LICENSES.md`에 출처·라이선스·작성자를 적고, CC-BY는 게임 내 크레딧 화면에 표시합니다.
라이선스가 불분명한 에셋, CoH3·Burning Bridges의 자료는 쓰지 않습니다.

**양식 방향:** Claude가 코드로 만드는 아트는 사실적 디테일보다 **실루엣이 분명하고 색이 절제된 양식**이 강점입니다.
그래서 "사실적이고 차분한 톤 + 단순화된 형태"로 통일하고, 처음부터 끝까지 같은 방식으로 만들어 일관성을 지킵니다.

## 7. 작업 방식 (1인 + Claude)

- **작업 카드:** 세션을 시작할 때 한 줄씩 적습니다: 목표 / 담당 시스템 폴더 / 관련 SPEC 줄 / 테스트 / 완료 조건.
- **세션 하나 = 작업 하나 = 커밋 하나.** `npm run check`, `npm test`가 통과해야 커밋합니다.
- **규칙이 바뀌면** 같은 커밋에서 SPEC.md를 고칩니다.
- **작업 기록:** 작업을 마칠 때마다 `docs/dev-log.md`에 한 일, 다음 할 일, 막힌 것을 적습니다.
- **단계 끝:** 휴대폰에서 실행해 보고 짧은 영상이나 GIF를 남깁니다(개발 일지·홍보용).
- **legacy:** D3이 끝날 때까지 v214를 플레이 가능하게 두고 기능을 추가하지 않습니다. v214는 게임플레이 참고용이며 데이터 기준이 아닙니다(데이터 기준은 CoH3).
